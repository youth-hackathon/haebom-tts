# Android 앱의 스트리밍 음성 연결

서버를 업데이트해도 기존 앱이 자동으로 스트리밍 재생·전사를 하지는 않습니다. 기존 `/tts`와 파일 `/stt`는 계속 사용할 수 있고, 앱에서 새 경로를 선택해 연결합니다. 아래는 앱 구현 지침이며, 이 저장소에는 Android 앱 소스 변경이 포함되어 있지 않습니다. 전체 메시지 규약은 [`streaming-api.md`](streaming-api.md)를 따릅니다.

## TTS: 파일 재생에서 PCM 재생으로

기존 `Speaker.kt`의 “완성된 음성 파일 저장 → 파일 재생” 경로는 기존 API용으로 남깁니다. 스트리밍 경로는 `POST /tts/stream`에 `{"text":"..."}`를 보내고, HTTP 본문을 한 줄씩 읽습니다.

OkHttp의 `ResponseBody.source()`에서 NDJSON 줄이 올 때마다 파싱합니다. `body.string()`이나 `body.bytes()`로 전체 응답을 기다리면 조기 재생 이점이 사라집니다. 응답 본문은 한 번만 소비하고 작업이 끝나거나 취소되면 닫습니다. [OkHttp ResponseBody 문서·소스](https://github.com/square/okhttp/blob/master/okhttp/src/commonJvmAndroid/kotlin/okhttp3/ResponseBody.kt)

음성 이벤트 처리 순서는 다음과 같습니다.

1. `audio.data`를 base64 디코딩합니다.
2. `sample_rate`, `channels`, `encoding`을 확인합니다. 현재 서버는 24kHz·mono·PCM16 LE를 보냅니다.
3. `AudioTrack`의 `MODE_STREAM`에 순서대로 PCM을 씁니다. 기기의 최소 버퍼 크기를 확인하고, 충분한 첫 조각이 모이면 재생을 시작합니다.
4. `done` 이후에는 새 조각을 기다리지 않고, 이미 쌓인 음성은 끝까지 재생합니다.
5. `error` 또는 `done` 없는 EOF는 실패로 처리합니다.

네트워크 읽기·오디오 쓰기는 메인 UI 스레드에서 하지 않습니다. 오디오 큐에 상한을 두고, 쓰기 결과가 부분 쓰기·오류인지 확인합니다. 네트워크가 빨라도 오디오 재생 속도에 맞춰 소비합니다. `AudioTrack`의 스트리밍 모드와 버퍼 사용법은 [Android 공식 문서](https://developer.android.com/reference/android/media/AudioTrack)를 따릅니다.

기존 앱이 보내는 `speed: 0.9`는 `/tts/stream`에 그대로 보내지 않습니다. 새 경로는 `speed` 생략 또는 `1.0`만 받습니다. 느린 안내가 필요하면 앱의 `PlaybackParams` 등 재생 속도 조절을 적용합니다. 기존 `/tts`의 서버 속도 조절은 유지됩니다.

## TTS 시간 제한과 중단

기존 “1.5초 안에 WAV 전체 수신” 마감은 스트리밍 경로에 적용하지 않습니다. 첫 음성 조각 대기, 조각 사이의 정체, 전체 생성 종료를 별도로 관리합니다. 첫 응답에 1.5초 목표를 유지할 수 있지만, 서버나 네트워크가 항상 그 시간 안에 답한다고 보장되지는 않습니다.

- 첫 음성이 오기 전에 실패하거나 대기 시간이 끝나면 서버 호출을 취소한 뒤 기존 폰 TTS로 전환할 수 있습니다.
- 이미 재생한 문장을 자동으로 처음부터 다시 읽으면 같은 안내가 겹칩니다. 재생 도중 오류의 정책은 별도로 정합니다.
- 새 안내가 오거나 화면을 떠나면 이전 HTTP 호출을 `cancel()`하고, 이전 `AudioTrack`을 멈추고 버퍼를 비워 해제합니다.
- 요청마다 앱 내부 식별자를 두어 취소된 작업의 늦은 오디오가 새 재생 큐로 들어오지 않게 합니다.
- `done`은 생성 완료이고 재생 완료는 아닙니다. 마지막 음성 조각을 잘라 버리지 않습니다.

## STT: 녹음하면서 전송

앱 매니페스트의 `RECORD_AUDIO`와 사용자 런타임 권한 허용이 필요합니다. 녹음은 사용자가 시작했을 때만 켜고, 종료·취소·연결 오류·화면 종료 시 즉시 멈추고 해제합니다.

1. `ws(s)://<서버>/stt/live`에 연결하고 `status: ready`를 기다립니다. 이 단계는 마이크를 켜기 전 미리 할 수 있습니다.
2. `{"type":"start"}`를 보내고 `started`를 기다립니다.
3. `AudioRecord`로 PCM16·mono·16kHz를 얻어 권장 100ms(3,200바이트)씩 바이너리 WebSocket 메시지로 보냅니다.
4. 사용자가 마치면 녹음을 멈추고, 마지막 남은 PCM 조각까지 보낸 다음 `{"type":"stop"}`을 보냅니다.
5. `final` 구간을 누적하고 `done`을 받으면 이번 결과가 끝난 것입니다. 준비된 소켓에서 다음 발화를 시작할 수 있습니다.

기기의 16kHz 녹음 지원 여부와 초기화 상태, 실제 읽은 샘플 수를 확인합니다. 다른 샘플레이트를 쓴다면 실제로 리샘플링합니다. PCM 샘플을 바이트로 옮길 때는 little-endian으로 직렬화합니다. WAV/MP4 헤더를 붙이지 않고, 바이너리 데이터를 JSON 문자열이나 base64로 보내지도 않습니다. [AudioRecord 공식 문서](https://developer.android.com/reference/android/media/AudioRecord)

`interim.text`는 화면의 현재 중간 자막을 교체하고, `final.text`는 확정된 구간으로 누적합니다. 예를 들어 중간 자막이 “설정”, 다음에 “설정 버튼”으로 오면 “설정설정 버튼”으로 붙이지 않습니다. 확정 문장과 아직 바뀔 수 있는 중간 자막을 따로 보관합니다.

## 연결 상태와 재시도

앱 상태는 `연결 중 → 준비 → 녹음 → 확정 대기 → 준비`로 관리하면 됩니다. 한 소켓에서 앞 발화가 끝나기 전에 다음 발화를 겹쳐 보내지 않습니다. 90초 대기·10분 세션 제한이나 네트워크 전환으로 소켓이 닫힐 수 있으므로 다시 연결할 수 있어야 합니다.

연결이 끊기면 진행 중인 녹음과 전송을 멈춥니다. 재연결 자체는 가능하지만 사용자가 시작하지 않은 녹음을 자동으로 재개하거나, 전사 성공 여부를 모르는 발화를 조용히 중복 전송하지 않습니다. 로그에는 API 키가 필요하지 않으며 앱에 Gemini 키를 넣지 않습니다.

Android 에뮬레이터·USB 연결 개발에서는 기존처럼 `adb reverse tcp:8766 tcp:8766`을 사용할 수 있습니다. 외부 배포 앱은 HTTPS/WSS 서버 주소를 사용합니다.

## 앱 통합 완료 확인

- 기존 `/tts` 호출과 폰 TTS fallback이 계속 동작한다.
- 스트리밍 TTS의 첫 소리가 전체 생성 완료 전에 재생된다.
- 긴 안내 도중 새 안내를 요청하면 이전 음성이 섞이지 않는다.
- 느린 네트워크·중단된 응답에서 오류와 취소가 처리되고 오디오 자원이 남지 않는다.
- STT 중간 자막이 반복 누적되지 않고, `done` 뒤 최종 문장이 한 번만 전달된다.
- 마지막 음절이 포함된 PCM까지 보내고 `stop`을 보내므로 문장 끝이 잘리지 않는다.
- 같은 소켓에서 두 번 말하기, 소켓 만료 후 재연결, 마이크 권한 거부를 처리한다.
- 실제 기기에서 첫 음성 도착·재생 시작·첫 글자·말한 뒤 확정 시간을 따로 측정한다.

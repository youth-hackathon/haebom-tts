# 스트리밍 TTS · Live STT 규약

기존 `POST /tts`와 `POST /stt`는 그대로 유지합니다. 이 문서는 같은 Python/Docker 서버에 추가된 두 경로의 규약입니다. 앱의 녹음·재생 코드도 이 규약에 맞춰야 스트리밍의 지연 감소를 얻을 수 있습니다. Android 변경 사항은 [`android-streaming.md`](android-streaming.md)에 있습니다.

| 경로 | 입력 | 출력 | 용도 |
|---|---|---|---|
| `POST /tts` | 텍스트 JSON | 완성된 WAV | 기존 앱 호환 |
| `POST /stt` | MP4·WAV 등의 파일 | 최종 텍스트 JSON | 파일 전사 |
| `POST /tts/stream` | 텍스트 JSON | NDJSON 음성 조각 | 조각 도착 즉시 재생 |
| `GET /stt/live` WebSocket | 시작·종료 JSON과 바이너리 PCM | 중간·최종 텍스트 JSON | 마이크 실시간 전사 |

TTS는 전용 TTS 모델의 HTTP 스트리밍이고, STT는 Live 전사 모델의 WebSocket입니다. 앱은 Gemini에 직접 연결하지 않습니다. `GEMINI_API_KEY`는 서버에만 둡니다.

## 스트리밍 TTS

### 요청

```bash
curl --no-buffer --fail-with-body http://127.0.0.1:8766/tts/stream \
  -H 'Content-Type: application/json' \
  -d '{"text":"설정 버튼을 눌러 주세요."}'
```

| 필드 | 규칙 |
|---|---|
| `text` | 필수 문자열. 앞뒤 공백을 제거한 뒤 1~300자. 초과하면 자르지 않고 400 |
| `engine` | 생략하거나 `"gemini"`. 이 경로는 `TTS_ENGINE`과 관계없이 Gemini 사용 |
| `speed` | 생략하거나 숫자 `1.0`. 다른 값은 400; 재생 속도는 앱에서 조절 |

요청 JSON은 최대 64KiB, 생성된 PCM은 최대 16MiB입니다. 전체 생성 제한은 `GEMINI_TIMEOUT_SECONDS`(기본 60초, 1~300초)입니다. 모델은 `GEMINI_TTS_MODEL`(기본 `gemini-3.8-flash-tts`), 목소리는 `GEMINI_VOICE`(기본 `Kore`)입니다. 스트리밍 결과는 캐시하지 않습니다. 기존 `/tts`의 완성 WAV 캐시·속도 조절은 그대로입니다.

### 응답

성공 스트림은 HTTP 200, `Content-Type: application/x-ndjson`입니다. UTF-8 JSON 하나마다 줄바꿈(`\n`)이 붙습니다. 네트워크에서 받은 청크 경계와 JSON 줄 경계는 다를 수 있으므로 줄바꿈까지 모아서 파싱합니다. 아래 `data`는 형식 설명용입니다.

```json
{"type":"audio","data":"<base64 PCM>","sample_rate":24000,"channels":1,"encoding":"pcm_s16le"}
{"type":"audio","data":"<base64 PCM>","sample_rate":24000,"channels":1,"encoding":"pcm_s16le"}
{"type":"done"}
```

- `audio.data`를 base64로 풀면 **24kHz, mono, signed PCM16 little-endian**입니다. WAV 헤더가 없으며 각 조각은 독립된 WAV 파일이 아닙니다.
- 조각을 순서대로 재생 큐에 넣습니다. 전체 본문을 모으거나 `Content-Length`를 기다리지 않습니다.
- `done`은 정상적인 **생성 완료**입니다. 앱의 재생 큐가 비었다는 뜻은 아닙니다. 남아 있는 음성은 끝까지 재생합니다.
- WAV 파일도 필요하면 성공한 PCM 조각을 이어 붙이고, 마지막에 길이가 맞는 WAV 헤더를 생성합니다.
- 사용자가 취소하거나 새 안내가 오면 HTTP 요청과 앱 재생 큐를 함께 취소합니다. 서버는 클라이언트 연결 종료 시 진행 중인 스트리밍 호출을 정리합니다.

요청 검증·키 미설정처럼 스트림 시작 전에 확인한 오류는 200이 아닌 HTTP 상태와 `{"error":"설명"}`으로 옵니다. 이미 HTTP 200을 보낸 뒤 실패하면 같은 스트림에 오류를 보냅니다.

```json
{"type":"error","message":"음성 생성에 실패했습니다."}
```

스트림 시작 전 오류는 400(요청 검증), 403(다른 웹 출처), 408(요청 본문 대기 시간 초과), 413(요청 크기 초과), 503(키·서버 설정), 502(Gemini 실패)로 구분합니다.

`error`를 받거나 `done` 없이 연결이 끝나면 실패입니다. 일부 음성이 먼저 왔더라도 성공으로 표시하지 않습니다. 오류의 설명 문자열은 사용자 안내용이며, 문자열 자체를 조건문으로 비교하지 않습니다.

## Live STT

### 연결 준비와 한 번의 발화

로컬 주소는 `ws://127.0.0.1:8766/stt/live`, HTTPS 배포에서는 `wss://<서버 주소>/stt/live`입니다. 일반 HTTP GET만 보내면 426, 키 미설정은 503, 다른 웹 출처의 요청은 403입니다. WebSocket 업그레이드 전에는 JSON `error`, 업그레이드 후에는 아래 이벤트를 처리합니다. 준비된 연결은 같은 사용자의 다음 발화에 재사용할 수 있습니다. 다른 사용자·동시 발화는 각각 별도 WebSocket을 사용합니다.

순서는 다음과 같습니다.

```text
앱                              서버
WebSocket 연결 ---------------->
              <---------------- {"type":"status","status":"connecting"}
              <---------------- {"type":"status","status":"ready","setup_ms":...}
{"type":"start"} ------------->
              <---------------- {"type":"started"}
바이너리 PCM 조각 ------------->
바이너리 PCM 조각 ------------->
              <---------------- {"type":"interim","text":"설정 버튼"}
바이너리 PCM 조각 ------------->
{"type":"stop"} -------------->
              <---------------- {"type":"final","text":"설정 버튼을 눌러 주세요."}
              <---------------- {"type":"done"}
              <---------------- {"type":"status","status":"ready"}
```

시작·종료 같은 JSON 제어 메시지는 최대 1,024자입니다.

처음에는 `ready`를 기다리고, `start`를 보낸 뒤 `started`를 받으면 오디오를 보냅니다. 마지막 PCM 조각까지 보낸 **뒤에** `stop`을 보냅니다. `done`을 받고 연결이 준비되면 다음 `start`를 보낼 수 있습니다. 한 연결에서 겹치는 발화는 지원하지 않습니다.

`interim`, `final`, 완료 이벤트의 도착 간격과 개수는 모델에 따라 달라집니다. 발화 도중에도 최종 구간이 올 수 있으므로, 위 예시의 순서 하나만 가정하지 않습니다. 완료 판단은 서버가 정리해 보내는 `done`으로 합니다.

### 오디오 형식

| 항목 | 값 |
|---|---|
| 전송 프레임 | WebSocket **바이너리** 메시지 |
| 인코딩 | signed PCM16 little-endian, 헤더 없음 |
| 샘플레이트 | 16,000Hz |
| 채널 | mono |
| 권장 조각 | 100ms = 1,600 samples = 3,200 bytes |
| 프레임 최대 | 64KiB, 비어 있지 않은 짝수 바이트 |
| 발화 최대 | 120초; 총 PCM도 120초분 이하 |

WAV 파일의 앞 44바이트를 무조건 잘라 쓰지 않습니다. WAV의 데이터 위치는 부가 청크에 따라 달라집니다. 실제 WAV 파서로 PCM을 꺼내거나 변환합니다. MP4·AAC·WebM 등 압축된 파일 바이트도 그대로 보낼 수 없습니다. 파일은 기존 `/stt`로 보내면 서버가 변환합니다.

마이크가 44.1kHz·48kHz로 녹음되면 앱에서 16kHz로 리샘플링하고 stereo라면 mono로 변환합니다. 샘플레이트만 16kHz라고 표시해 보내면 음성과 전사 결과가 잘못됩니다.

### 서버 이벤트

| `type` | 주요 필드 | 앱 처리 |
|---|---|---|
| `status` | `status: connecting / ready / disconnected`, 최초 `setup_ms` | 연결 상태 표시. `setup_ms`가 없으면 기존 측정값 유지. `disconnected` 뒤 재연결 |
| `started` | 없음 | 이번 발화 PCM 전송 시작 |
| `interim` | `text` | 현재 중간 자막을 **교체**. 매번 이어 붙이지 않음 |
| `final` | `text` | 확정 구간을 누적하고 해당 중간 자막을 비움 |
| `done` | 없음 | 이번 발화 정상 완료. 최종 텍스트를 다음 작업에 사용 |
| `error` | `message` | 이번 작업 실패. 녹음 중지·자원 해제 후 연결 상태 확인 |

빈 `final.text`가 올 수 있습니다. 모델이 최종 전사 이벤트 자체를 보내지 않으면 서버는 최대 20초 기다린 뒤 오류로 종료하며, 임의의 빈 최종 문장이나 성공 `done`을 만들지 않습니다. 성공 완료 전에 연결이 끊기거나 오류가 나면 미완료입니다. 사용자가 직접 취소할 때는 `{"type":"cancel"}`을 보내거나 소켓을 닫습니다. 취소는 해당 연결을 종료하므로 다시 사용하려면 재연결합니다.

서버는 연결 준비와 발화 종료 후 결과를 각각 최대 20초 기다립니다. 준비된 상태에서 90초 대기하면 연결을 종료하고, 연결 하나의 최대 유지 시간은 10분입니다. 연결이 항상 살아 있다고 가정하지 말고 종료를 감지해 다시 준비합니다. 마이크 녹음은 사용자의 시작 동작으로만 재개합니다.

### 시간 측정

- **연결 준비:** WebSocket 연결 시작부터 `ready`까지. 서버의 `setup_ms`는 서버 내부 Gemini 준비 구간이며 앱↔서버 왕복 지연은 포함하지 않습니다.
- **첫 글자:** 실제 PCM 입력 시작부터 첫 비어 있지 않은 `interim` 또는 `final` 수신까지.
- **최종 확정:** 마지막 PCM 전송과 `stop` 이후 `done` 수신까지.
- **TTS 첫 음성:** 요청 시작부터 첫 `audio` 수신까지. 실제 스피커 출력은 앱 버퍼와 오디오 장치 지연이 추가됩니다.

녹음 길이 전체와 최종 확정 지연을 합쳐서 “모델이 몇 초 걸렸다”로 표시하지 않습니다. 이전 웹 체험의 측정값과 서버·앱 경로가 다를 수 있으므로 이 서버에서도 같은 조건으로 다시 측정합니다.

## 실제 API로 확인하기

서버를 실행하고 `GEMINI_API_KEY`를 설정한 뒤, 이 저장소에서 실행합니다. 검사하는 컴퓨터에 FFmpeg도 필요합니다.

```bash
python -m pip install -r requirements.txt
python check_streaming.py --url http://127.0.0.1:8766 --out runs/streaming
```

스크립트는 서버에 TTS를 요청해 PCM 조각을 WAV로 저장하고, 이를 16kHz로 변환해 Live STT에 실시간 속도로 전송합니다. 기본값은 같은 연결에서 두 번 전사입니다. `--text`로 문장을, `--turns 1`~`3`으로 반복 횟수를 지정할 수 있습니다. API 키는 검사 스크립트에 전달하지 않고 서버에서 사용합니다.

이 명령은 **실제 Gemini 호출과 사용량을 발생시킵니다.** `python -m unittest discover -s tests -v`가 실행하는 모의 응답 테스트와 별개이며 자동 실행되지 않습니다. 결과는 출력 폴더의 `result.json`과 `streaming-tts.wav`에 남습니다.

2026-11-21 Python/Docker 서버의 한 문장 점검에서 TTS 첫 조각은 1.306초, 마지막 조각은 2.111초, 완료 확인은 2.167초였습니다. 연결 준비는 0.459초였고, 연결을 재사용한 두 STT 발화는 첫 글자 1.204/1.203초, 전송 종료 후 확정 0.382/0.343초였습니다. 두 번 모두 “안녕하세요, 해봄입니다. 설정 버튼을 눌러주세요.”를 반환했습니다. [측정 원문](../results/streaming/result.json)

수치는 네트워크 수신·처리 시점이며 실제 스피커 출력이나 사람의 마이크 입력 지연을 측정한 것이 아닙니다. 한 문장 왕복 성공을 확인한 결과로, 여러 문장·네트워크·발음 조건의 성능 보장은 아닙니다.

## 배포 경로

Docker의 기본 포트 매핑은 로컬 `127.0.0.1:8766`입니다. 외부 앱에 서비스할 때는 HTTPS/WSS 주소를 제공하는 프록시를 앞에 둡니다. 프록시가 WebSocket `Upgrade`를 전달하고, `/tts/stream`의 응답을 통째로 버퍼링하지 않도록 설정합니다. 프록시 대기 시간도 위 발화·세션 정책과 맞춰야 합니다. 브라우저의 `Origin`이 있으면 요청의 Host와 같은 호스트·포트만 허용하므로 프록시는 원래 Host를 전달해야 합니다. 네이티브 앱처럼 `Origin`이 없는 클라이언트는 이 검사 대상이 아닙니다.

이 저장소의 스트리밍 경로는 Python/Docker 서버용입니다. 앞서 만든 웹 체험 사이트의 `/api/tts/stream`, `/api/stt`는 별도 배포의 경로이므로 앱 주소를 혼동하지 않습니다.
